# Claude 靠做梦整理记忆

2026 年 11 月 6 日，Anthropic 官方账号发了一条帖。

大意是，记忆让 Claude 能从经验里学习；新工程博客讲「做梦」如何帮它整理学过的东西，纠正错误，下次更快找到该找的内容。

帖子发出后大约 131.8 万曝光，1.1 万赞，982 转，810 回复，622 引用，9721 书签。

原文标题是 *The components of agent memory*，作者 Lance Martin，发布于 Anthropic Engineering Blog。

本文是对这篇博客的中文整理与剖析。

数字与机制以原文为准；穿插的判断，是我读完以后的落地看法。

## 记忆这件事，先划清边界

克尔凯郭尔写过：人生只能向后理解，却必须向前活。

Anthropic 说，给 AI agent 设计记忆，也卡在类似的地方。

人一边过日子一边编码记忆。海马体负责当场抓住经验，让记忆很快形成、马上可用。

但只有一部分会被巩固成长期知识。

大量巩固，发生在大脑「下线」的时候。睡觉、安静休息时，海马体重放近期经验，再慢慢蒸馏、并入新皮层。

Agent 也可以做类似分工。

Agent 的工作大量留在日志或对话记录里。Letta 和 UC Berkeley 的研究者提出过 sleep-time compute：模型在交互空档整理既有上下文。

同一思路用在记忆上，就是对着日志反思，修错，写新笔记，或换新表征。这套过程常被叫作 dreaming，做梦。

Anthropic 写得很清楚。这里的「agent memory」，特指 Claude 从经验里学到、并在会话之间留下来、以后还能读回的知识。

它排除三类东西。

权重更新不算，那是训练时改内部参数。

单次对话里的 in-context learning 只活在当前窗口，也不算。

Compaction 同样排除。那是 Claude 自己写摘要，替换更早的轮次，好在新上下文窗口里继续干活。

记忆笔记，就是 Claude 把重要事件标出来，或写进记忆目录，方便以后找。

## 记忆，是对未来需求的一次预测

写下一则规则，等于在预测这个模式以后还会用得上。

记下一条已核实的事实，等于在预测未来会话会直接依赖它，不必再核对一遍。

Anthropic 用 Continual Learning Bench（CL-Bench）1.0 里的一个任务说明这件事。

任务要求 Claude 查数据库、连续回答一系列问题。答完后告诉它正确答案，它可以把记忆写下来，帮助答后面的题。

记忆可以撑起一个学习闭环。答错，记录失败，提出理论，检验理论，再沉淀成以后怎么答的规则。

实验里，每个问题都开全新会话；唯一例外是，可以从跨会话持久存在的记忆目录里取文件。跑的是 Claude Managed Agents。

不同模型，做成闭环的程度差很多。

Claude Sonnet 4.6 能走到「为什么答错」的理论生成。记忆目录里散落着许多文件，每份列着若干未检验的猜测。

Claude Opus 4.7 把笔记收成一份参考文档，开始标哪些事实已核对、哪些还没确认。

Claude Sonnet 5 在评分器核对后，把每个答案标成已确认；答错就写一条纠正。

Claude Opus 5 是这一系列里第一个真正闭环的。多数条目里既有规则，也写明「怎么知道这条规则成立」，还附上之前的答案，以及对沿途陷阱的明确警告。

Claude Opus 5.5 和 Claude Sonnet 5.5 同样闭环，用记忆记下「如何更好回答未来问题」的已验证规则。有记忆时，两者得分与 Opus 5 大致相当；无记忆基线略高一点。

我读到这里的第一反应是，记忆系统真正拉开差距的，是存完之后会不会自测。

猜很多、验很少，目录会越来越像乱纸堆。

核对并纠错，再写成可复用规则，目录才开始像资产。

## Claude 学会了判断什么值得记

Anthropic 还用《宝可梦红》测 Claude 对显著性的判断。

长程任务，状态一直变，记错方向的代价特别大。

每轮开始，模型拿到一个可读写的记忆文件夹。对比大约进行到 1 万步时，Claude Sonnet 3.7 与 Claude Fable 5 各跑一轮的记忆目录。

这差别主要在「什么值得记」。

Sonnet 3.7 默认什么都可能重要，写得很滥。从遭遇到 NPC，常常各开一份文件。最终写了 413 个记忆文件，散在 225 个文件夹里，只拿了 1 枚徽章。

Fable 5 写了 9 个文件、2 个文件夹，外加顶层一份 `global.md`，拿了 4 枚徽章。

Sonnet 3.7 的麻烦更大。

宝可梦游戏状态一直在变，它那份细账很快过时。越往后，越要把时间花在翻记忆上，而不是玩游戏。

大约第 1 万步，它又开了第四个「master」记忆文件夹。随后 17 步里，新建 6 个文件、删掉 9 个，游戏里一步都没走。

Fable 5 记的是游戏屏幕不会直接告诉你的东西。

玩家有多少钱、人在地图哪，每回合屏幕都能读到，写进记忆等于重复劳动。

策略、计划、测过的规则，只有 Claude 自己推出来、写下来，才会留下来。

所以 Fable 5 的 `global.md` 像仪表盘，装着当前目标、打道馆预案，以及自己用记忆的规则。`locations` 放路线导航计划，`gameplay` 放基于实战的策略。

有个细节很典型。连续 7 个精灵球都没抓到鲤鱼王之后，Claude 写下：「如果连续 3 个以上球失败，改变时机（在菜单步骤之间多插 wait）。这样改完马上就抓到了。」

记忆文件夹小得多，Fable 5 反而推得更远。Opus 5.5 做法类似，小文件夹盯住当前目标和下一步，边玩边改写，最后通关。

显著性，本质是压缩。

把随时能读到的状态塞进磁盘，等于把噪声当成资产。

把推出来的规则留下来，才是跨会话真正增值的那一层。

## 怎么引导 Claude 写记忆

Anthropic 的结论很干脆：告诉 Claude 记忆是干什么用的，但不要规定它怎么用。

在 CL-Bench 上，他们只说「有一个记忆文件夹可用」。对 Opus 4.7 和 Opus 5，这点笼统指引就够用，而且带来明显提升。

他们也测过「每条规则单独规定该写什么」。其中一条是「只记录失败」。

结果是，Opus 5 和 Opus 4.7 都丢掉了记忆带来的大部分增益。

对更强的模型，把显著性判断交给它，比事先钉死规则更有效；钉死的规则反而可能伤表现。

引导对旧模型帮助最大。

比如 Sonnet 4.6 经常不读记忆目录，也不去检验「为什么答错」的理论。

这时提示它答前先读记忆、再明确检验理论，基准分几乎翻倍。

Sonnet 5 不用提示也会这么做，答前读记忆的比例是 10 次里 9 次。Sonnet 4.6 不到一半。

对前沿 Claude，Anthropic 通常只给简单指引。人要求时写记忆，或者明显值得记时写，判断交给 Claude。

做产品的人很容易踩反。

一上来就规定「只记失败」「只记结论」「必须按某模板」，看起来整齐，其实把模型本来会用的成功模式也抹掉了。

告诉它记忆服务于什么目标，比告诉它记忆文件里必须出现哪几个字段，往往更管用。

## 做梦能纠正错误的记忆

会话里按当场显著性写下来的笔记，从一开始就可能错；环境一变，也可能漂。

后面会话如果读到、又信了，就会踩坑。

做梦提供一条路。拿原始会话记录当对照，检验笔记。

宝可梦里有个很具体的例子。

过月见山（Mt. Moon）时，入口在西、出口在东。入口附近有一截单向悬崖，掉下去就回到来时的路线，很难爬回。

Claude 把入口的宝可梦中心当路标。它以为中心在哪一侧，决定它会不会走下悬崖。

某次它错误地写下，宝可梦中心在东侧。走出中心后宣布「月见山已经在身后了」，笔记也改成「Mt Moon DONE」。

其实月见山根本没过。几步之后掉下悬崖，又回到来时的路线。导航工具没显示坠落，Claude 结论变成「我朝西冲过头了」，并且以为自己一直在正确一侧。

事实不是这样。

Anthropic 让做梦跑在这份错误位置笔记上。对照会话记录，抓到错误，改写笔记。

改对以后，Claude 直接回月见山，最终到了华蓝市。

未纠正的那一轮，同一条旧路线掉回去三次。第三次失败后，Claude 写下类似「我要停，别再空转了」。自动回复让它继续，于是一路退回月见山前的深灰市，想恢复补给。整轮跑完，始终没到华蓝市。

无记忆、原始错误记忆，都没过山；做梦纠正后过了。

这对我很有启发。

很多 agent 产品只做「写记忆」，不做「对账」。

错笔记一旦被后面会话当权威，会系统性放大。

做梦的价值，首先是给记忆加一层可审计的回放。

## 做梦能建新的记忆表征

做梦不只修错，也能建表征，方便在越来越大的知识库里穿行。

其中一类叫 wiki：Claude 自己写、自己维护的页面集合，把某一主题的知识收拢，并链到其他笔记。链接相当于一张地图。

Anthropic 用收购收购公司 Stainless 的内部语料做了实验。大约 35 万个文件，约 4.2 亿 token。评测集是 25 个问题，并给 Claude 搜索工具。同时要求用做梦基于这些文件建 wiki。

128 个会话里，提示 Opus 5 agents 去探索文件，写或改带链接的 wiki 页，合并重复，并对照源文件核验主张。会话之间用共享日志协调，后一轮接着前一轮的进度。

做梦从 2 场扩到 128 场，25 题得分从满分标准的 13% 提到 48%。

早期 wiki 像新员工的知识；多梦几轮，地图变厚，更像老员工。

Wiki 最有用的时候，往往是和搜索一起用。搜索 + wiki，聚合分从 54% 升到 61%；只用搜索是 53%；只用 wiki 最好成绩是 48%。搜索加 wiki，大约还能每题省 2 万 token。

他们也测了哪些任务吃 wiki 红利。

Harvey LAB 基准 + 一批并购文件。一类是 24 道并购相关题，一半以上要跨多份文件找信息，不少还要判断或算数。这类题上，查 wiki 得 87%，只用搜索得 73%。

另一些任务上，wiki 没明显优势。有的 LAB 任务，多数评分项单文档文本搜索就能拿满，wiki 相对搜索看不出增益。

还有一次，wiki 长得比源文件还大。Anthropic 引用博尔赫斯《论科学的精确性》里那张和帝国一样大的地图：细节极多，等于什么都没抽象。

表征不是越大越好。

地图比领地还大，导航成本会反超。

## 做梦能把笔记往记忆层级上推

做梦还可以把笔记浮到记忆层级顶层，由 agent harness 在每个新会话开始时预加载进上下文。

Claude 不必先搜索，甚至不必先知道「有东西可搜」。

预注入要小心。

注入会吃宝贵 token；错误笔记会进每一个会话。加载也不等于遵从：Claude Code 文档提醒过，指令文件越长，遵从度往往越低。

所以顶层必须保持相对小。做梦在这里的大量工作，是把细节往下压，顶层只留索引和链接。

Claude Code 的 auto memory 也是同一逻辑。它不把全部 auto memory 塞进每次上下文，只加载 `MEMORY.md` 的前 200 行或 25 KB。这段头充当索引，告诉 Claude 自己知道什么、去哪找。

做长期 agent 产品，可以把记忆想成三层。

顶层：极少、极稳、每会话默认可见。

中层：按任务检索的笔记与 wiki。

底层：原始日志，做梦时拿来对账。

顶层膨胀，通常是系统开始变笨的前兆。

## 做梦能按具体目标塑形记忆

做梦还能决定记忆往哪边长。

像 Claude Duet 这类助手，记忆常常要围着「正在帮的这个人」组织；做梦指令可以调成服务某个具体目标。

LAB 基准里有个收购收购模拟任务，给一批合同，brief 按合同条款描述是否正确来评分。

一开始的建 wiki 指令，没告诉 Claude 怎么用 wiki。任务高度依赖合同条款。建库时，多个 agent 同时往同一张共享条款表里写。

结果关键事实缺失。用这份 wiki 生成的 brief，57 条事实里只保住 41 条，约 72%。共享表摘要差，还互相覆盖，有的条款直接没了。

合同条款本该是 wiki 最重要的部分，指令却没写明。

他们跑了一个循环。Claude 反思失败，提议改指令，再重建 wiki。Claude 自己发现必须紧跟合同条款，于是重写建库指令。

每份合同单独一页，由单个 agent 写，条款逐字引用，不再摘要进共享表。

改进后的 wiki 生成 brief，评分项从 72% 提到 100%，57 条全保住。

做梦还能补上单次会话留下的空洞。

写笔记时，Claude 只看见当时那一窗上下文。做梦可以跨很多会话找共同模式、修共同错误。

LAB 建 wiki 时，Claude 有时会链到尚未创建的页面。第二轮做梦合上不少缺口。有一任务里找到 9 条指向缺失页的链接，改指到同一文档已有页面；还新增 3 页，含一个索引。

目标不写进做梦指令，记忆就会跟着「写起来方便」长，评分真正看的东西排不上号。

你要的是可引用的条款，系统却在优化一张大家抢着改的摘要表，分数自然掉。

## 还没想清楚的问题

Anthropic 自己列了几道开放题。

第一，什么时候该创建记忆。任务进行中写记忆，显著性当场抓住，下一轮马上可用；但写笔记会分心。做梦把创建推到后台，输出却未必立刻可用。

第二，怎么让记忆可靠地保持更新。错误预测，一开始就写错的规则，环境变了以后漂掉的笔记，都需要算力去修。让 Claude 持续检查全部记忆，未必划算。更现实的是，把做梦聚焦在「容易变」的信息上，或按访问频率调做梦节奏。

第三，是否把 transcript 搜索当作记忆底座。表征（比如 wiki）加搜索，有时有效；但维护表征要算力，还得防错误和幻觉堆积。

模型对显著性的判断在变好，但没有模型真知道未来几轮会发生什么。

做梦给 Claude 一个向后看、用算力整理记忆的机会。它可以纠错、维护表征，让未来会话更容易取用。

记忆系统会跟着 Claude 能力一起演化。Anthropic 说，关于怎么设计 Claude 的记忆系统，他们还有很多要学。

## 对我意味着什么

如果你在做 agent、副业自动化，或任何「跨很多天还能接着干」的产品，这篇博客几乎是一份可对照的清单。

先分清你说的记忆是哪一种。权重更新、窗口内学习、摘要压缩和跨会话笔记，别混着吹。

再问显著性。你在存「屏幕上随时能读到的状态」，还是「推出来才存在的规则」？前者膨胀，后者复利。

写记忆的提示，优先说目标，少钉死字段。强模型被「只记失败」这类规则绑住，增益会掉。

务必给做梦预算。只写不梦，错笔记会成为永久权威。至少要有对照原始日志纠错、按目标重建表征，以及把顶层索引压小。

Wiki 不是装饰。跨文档、要判断、要计算的问题，它可能明显强于裸搜索；单文档能搜到的题，它可能白费。体量超过源材料时，先剪。

顶层注入要吝啬。参考 Claude Code，头 200 行或 25 KB 当索引，细节下沉，链接留下。

最后留一条可执行的自测。拿你自己产品里最容易翻车的长任务，看记忆目录是更像 Sonnet 3.7 的 413 文件，还是更像 Fable 5 的 9 文件加一份 `global.md`。

目录形状，往往比你写在 README 里的「我们有记忆」五个字，更能说明系统成熟度。
